Histórico da publicação automática (Actions)

Configuração do workflow Pages

O que foi feito

Passo a passo da hospedagem

Este é o percurso desde o projecto local até ao primeiro deploy.

01

Escolher GitHub Pages

Foi escolhida a opção gratuita de alojamento estático. Como o Pages não executa Node.js, a aplicação teve de preparar os ficheiros que podem ser servidos directamente pelo navegador.

02

Criar o repositório

Com a sessão GitHub iniciada, foi criado o repositório público BernardoReis1/duma-express, sem ficheiros iniciais, para receber o projecto existente.

03

Preparar o catálogo estático

Foi criada a tarefa de exportação que inicia o servidor temporariamente, consulta /api/products e guarda os dados em products.json. O catálogo exportado contém 62 produtos.

04

Apontar as páginas para o JSON

A página inicial e a página de produtos passaram a pedir products.json, em vez de chamar uma API que não existe no alojamento estático. Assim, pesquisa, categorias e cartões conseguem carregar o catálogo publicado.

05

Gerar a pasta de publicação

O comando de build copia as páginas HTML, CSS, JavaScript, catálogo, logótipos e fotografias para dist/. O código do servidor e os dados privados não são copiados para o site público.

06

Configurar publicação automática

Foi adicionado o workflow .github/workflows/pages.yml. A cada envio para main, o GitHub instala Node, constrói o site e publica o artefacto com GitHub Pages.

07

Enviar o projecto para o GitHub

A pasta foi inicializada como repositório Git, ligada ao remoto, preparada e enviada para a branch main.

git init --initial-branch=main
git remote add origin https://github.com/BernardoReis1/duma-express.git
git add --all
git commit -m "Publish Duma Express on GitHub Pages"
git push -u origin main
08

Seleccionar GitHub Actions

Nas definições do repositório, em Settings → Pages → Build and deployment → Source, foi seleccionada a opção GitHub Actions.

09

Validar o resultado

A execução do workflow terminou com sucesso. Foram carregados 62 produtos, sem imagens quebradas, e o site foi aberto no endereço público.

Automação

Como uma actualização chega ao site

Não é necessário voltar às definições Pages em cada alteração. O workflow faz o build e publica a nova versão quando recebe alterações em main.

✏️Editar ficheirosHTML, CSS, imagens ou servidor
→
⬆️Enviar para mainCommit e push para o GitHub
→
⚙️GitHub ActionsExporta catálogo e cria dist/

Depois, o job de deploy actualiza o site. O workflow pode ser acompanhado no separador Actions do repositório.

Comando para reconstruir localmente

npm run build:pages

Este comando actualiza products.json e cria a pasta dist/. A pasta gerada fica fora do Git através do .gitignore; o workflow constrói-a no próprio GitHub.

Importante

O que ficou funcional — e o que precisa de backend

GitHub Pages serve ficheiros estáticos. O navegador consegue mostrar as páginas e carregar o catálogo, mas não consegue executar o servidor Node que recebe e guarda formulários.

Funciona no site publicado

  • Páginas, estilos responsivos, logótipos e imagens.
  • Catálogo de 62 produtos carregado de products.json.
  • Pesquisa, filtros por categoria e detalhes dos produtos.
  • Carrinho guardado localmente no navegador e resumo do checkout.
  • Ligações directas de contacto, como email e WhatsApp, que não precisam de guardar um formulário.

Não é executado pelo GitHub Pages

  • Newsletter e formulários de contacto/criação de sites, que enviam pedidos para as APIs Node.
  • Registo de encomendas em /api/orders e confirmação do pedido pelo servidor.
  • Persistência central dos pedidos e subscrições em ficheiros JSON Lines.
Limite de funcionamento a conhecer No Pages, as rotas /api/... não existem. Por isso, os formulários e o fluxo de checkout que tentam primeiro registar o pedido podem apresentar erro em vez de o guardar/abrir para envio. O carrinho local e o catálogo continuam disponíveis. Para activar essas operações, é preciso publicar também o server.js num alojamento Node.js e ligar os pedidos do navegador ao endereço desse backend.

Para ter tudo funcional de ponta a ponta

Manter GitHub Pages para o site e alojar a API num serviço Node.js. Depois, configurar o endereço público da API para os pedidos de catálogo e formulários, aplicar as regras de segurança necessárias e testar newsletter, contacto, pedido de site e checkout. O GitHub Pages sozinho não consegue substituir esse backend.
